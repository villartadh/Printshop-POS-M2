# Native backup and restore — foundation
Native SQLite schemas differ from desktop SQLite schemas. A native encrypted backup is not a desktop restore file; legacy v0.2.0 desktop compatibility remains on the existing desktop path. No real shop data or credentials in tests.

Backup envelope v1: fixed magic, authenticated schema/size/salt/nonce header, AES-256-GCM with 128-bit tag and random salt/nonce, PBKDF2-HMAC-SHA256 600,000 iterations, independent operator backup passphrase, 32 MiB bounded payload, rejects wrong password, truncation, trailing bytes, changed header/ciphertext and unsupported schema. Plaintext decoded only after authentication; caller clears its buffers. Pure 20 JVM checks passed. This is an archive primitive, NOT a database backup or restore operation.

Next: owner-authenticated consistent native database snapshot into private staging (include committed WAL, exclude/revoke active sessions; validate integrity, schema, financial invariants); encrypted export via Storage Access Framework. Restore must validate decrypted candidate and migrate in isolated staging, require owner proof and stopped writer/closed shifts, preserve current backup and rollback journal, prohibit overwrite of live DB without explicit confirmation, reject mismatched source/schema and fail closed on interruption. Add fault/reopen/replay/actual emulator tests. Native/desktop synchronization is a separate authenticated protocol, not copying live databases. Keep preview fixture isolation and no physical/production claim.
