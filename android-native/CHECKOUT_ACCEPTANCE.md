# Native cash checkout — durable synthetic transaction foundation

Native checkout is under development. Phase 1 calculates a read-only confirmation. Phase 2 records synthetic sales/cash/stock atomically ONLY in the explicit checkoutFixture database. Default CatalogStore and all actual screens remain read-only for checkout. No actual customer payment, real inventory, tax issuance, network call, live data, physical or production acceptance.

## Implemented contract

- `CheckoutPlan`: immutable single-service cash confirmation from a saved active service, saved pricing revision, saved recipe revision and authoritative material snapshots. Uses integer centavos and exact PricingMath for count/document/area/linear/bulk, not editable quote price. Nonpositive sales, underpayment, hidden stale fields, unsupported quantities, duplicate materials and invalid revisions fail closed. Cash tender capped at maximum supported line total. Partial credit and electronic payments are not supported.
- Saved recipe materials use an explicit billable-unit or produced-item basis where advanced pricing requires it. Per-material required milliunits must be exactly representable in the existing stock ledger (fractional milliunits rejected, never silently rounded). Check pending stock request, exact available stock and catalog/stock revision per material. Cost is separate from selling price, summed before rounding.
- `CatalogStore.prepareCheckout`: one consistent SQLite read transaction reads catalog, pricing, recipe, material rows, ledger balances and pending request state. Revision mismatch requires fresh quote; preparing does not mutate any table. Preview cannot be used as evidence of paid sale.
- `Proposal.sameSnapshot` and `fingerprint()`: compare exact identity, inputs, revisions, selected rate, amount received/change, stock and material snapshots in sorted material order. Version tag CHECKOUT-PLAN-V1, canonical Java DataOutputStream fields (big-endian primitives, writeUTF with modified UTF-8; nullable fields have a presence flag); lowercase SHA-256. Fingerprint is for durable idempotency, not authentication/signature. Stale confirmation must fail, even if replenishment restores same balance.
- `CheckoutPreview.render`: plain-text confirmation preview, marked NOT RECORDED and NOT A TAX DOCUMENT OR PROOF OF PAYMENT. No native screen or print integration yet.

## Phase 2 — durable synthetic checkout transaction (schema v6)

- Additive schema v6 calls CheckoutJournal.create after the existing v1–v5 migrations. Old catalog, recipe, pricing, ledger and unresolved stock requests are preserved. The v5 migration is still subject to parent PR #12 verification; this v6 implementation is only on the existing stacked draft PR #13 and must not merge ahead of it.
- `checkout_requests` immutable payload includes request UUID, fingerprint version/hash, original input values, service/pricing/recipe revisions, original selling and cost totals, material count and state. `checkout_materials` stores original material snapshots; `checkout_sales`, `checkout_cash`, `checkout_stock_links` are immutable fixture records. SQL checks enforce integer monetary quantities, exact total/received/change, exact demand and exact stock link; triggers block update/delete/replacement of audit rows and invalid transitions.
- `CatalogStore.checkoutFixture(context, UUID)` is the only explicitly opted-in package-private writer, targeting `checkout-fixture-UUID.db`. The default preview database, normal constructor and all screens cannot stage/apply/cancel checkout. No real shop or customer records should ever be passed to the fixture API. Preserve this fence until native authentication/shift authorization and independent acceptance are implemented.
- Stage recalculates against authoritative revisions inside a write transaction, compares the reviewed Proposal, saves immutable payload and material snapshots, and returns PENDING. Pending does not reserve stock or represent payment received. Review first; do not auto-apply or auto-cancel. Pending list can recover by UUID/fingerprint after reopening. Before apply, rebuild the exact proposal against current data under a write lock. Reject stale stock, pending stock request or any changed confirmation. Atomically append sale, cash, one movement per material with distinct UUID and linkage, then APPLIED. A failed operation rolls everything back and the PENDING request remains. Exact replay returns the original recorded snapshot even after stock changes.
- Explicit cancellation requires matching fingerprint and a printable reason, only before recording; retains immutable state and cancellation reason, no movement/payment. Changed cancellation reason or a previously recorded request cannot be cancelled. No automatic discarding, refund or reversal. These are fixture-only records, not authority to receive actual cash.
- `Record.previewReceipt()` only for APPLIED, marked SYNTHETIC and NOT A TAX DOCUMENT / NOT PROOF OF REAL PAYMENT. No printing or native cashier screen yet.
- Host SQLite fixture test `python3 android-native/tests/checkout_journal_schema_test.py`: 220 checks across v1–v5 schema fixtures (actual SQLite DDL, rollback injection, exact records, terminal immutability and duplicate/competing stock constraints). Prior stock suite 76 host checks and 194 Java checks rerun, total 490 local checks. Parser: 3 modified Java sources, no syntax errors. CatalogStore/CheckoutJournal ordinary Java type compilation against minimal handwritten Android API stubs passed, NOT real Android build verification.
- Installed test now requires NATIVE_DURABLE_CHECKOUT_PASS after all prior markers: exact v5 fixture migration, preservation/recovery of pending stock; fixture-only write guard; two-material atomic rollback fault, close/reopen, exact same-identity race using two SQLite helpers, competing stale proposal, payment/link counts, historical replay after replenishment, pending manual stock fence, explicit cancellation. Actual Android CI not passed; no APK or installed claim.
