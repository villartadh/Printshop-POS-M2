# Native cashier authorization and shift accounting — schema v7 fixture milestone

Scope: existing major checkout branch, synthetic test databases only. This is not a live cashier login screen, real payment processor, or tax receipt system. Default preview database and actual Android screens remain unable to record checkout. No customer/shop credentials or real money.

## Implemented

- Explicit first-run owner setup in a NEW checkout fixture only, never an insecure default. One owner, owner-only creation/disable of cashier accounts; ASCII case-normalized unique usernames, no role escalation, no owner disable. Account disabling requires the operator's shift to be closed and invalidates previously issued sessions.
- `CashierSecurity`: 12–128 character nonblank passwords; per-account random 16-byte salt, PBKDF2-HMAC-SHA256 with 600,000 iterations and 256-bit result; constant-time comparison. Caller owns/wipes char arrays. No plaintext credential persisted, never log secrets. Random 256-bit session token; persist SHA-256 token digest only, account revision and 8-hour expiry, explicit revocation. Reject backward device time before issue, expired, revoked, disabled/changed account. Known-account lockout after five failed attempts for 60 seconds, persists failed-attempt state even when sign-in is denied. Unknown/denied accounts use generic refusal; synthetic local security foundation, not complete rate limiting or hardened device-clock/keystore protection.
- `CashierJournal` additive v7 schema: accounts, sessions, shifts and immutable checkout–operator–shift links. SQL constraints and triggers prevent role/identity changes, credential replacement, session renewal by mutation, multiple open shifts per operator, invalid closure and unlinked recorded checkout when accounts exist. Existing v1–v6 data retained; no default account inserted or retroactive attribution of legacy synthetic sales.
- Every authenticated fixture stage/apply/cancel/read checks live session and exact operator ownership; staging links to an open shift atomically. In the same transaction, reject changed proposal or unresolved manual stock, insufficient stock or drawer limit, and atomically record synthetic sale/cash and stock. Applied historical replay after shift closure returns original result, never new payment. Pending requests do not count as cash and prevent close. Cancel explicitly with immutable reason. The old v6 unauthenticated fixture experiment is intentionally available only before an account is initialized for previous isolated tests; setup is forbidden if legacy checkout journal already exists. Do not expose legacy methods or any fixture writer to the ordinary UI.
- Shift opening requires UUID and explicit opening cash; exact identity replay returns original, conflicting request or second open shift rejected. Closing counts actual cash, calculates expected = float + net applied cash (not gross tender), variance = counted − expected. Exact close replay only; no mutation of closed shift. One operator cannot access another operator's fixture checkout or shift; owner management does not bypass cashier ownership. Expense/drawer adjustment, partial payments, void/refund, multi-cashier shared drawer, forgotten credential recovery/password changes, role transfer, production device hardening and full audit logging remain separate pending scope.
