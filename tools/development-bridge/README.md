# Development Automation Bridge (pilot v0.1.0)
Read-only checkpoint coordinator for exact Printshop POS M2 PR workflow runs. No AI/API billing, external host, local PC agent, or privileged write token needed. Run Python unit tests from this directory; use `GITHUB_TOKEN` with Actions read access and `python ci_checkpoint.py --sha <40-character SHA>` on an authorized runner. Optional bounded polling is at most 30 minutes. Output contains only workflow metadata and a deterministic event key; no logs, user records or credentials.

Mandatory workflow IDs are pinned for this repository. Review is not merge approval: current branch/base, PR and all actual gates must independently be checked. Missing/cancelled/pending results cannot approve a merge. Any failure triggers diagnosis. Event key is an idempotency identifier, not a shared lock. Durable event consumption, transactional claims, workflow activation, installed skill/MCP integration and spontaneous ChatGPT activation are NOT implemented in this pilot. Do not run multiple writing workers; continue the existing hourly automation until a proven durable lease is available. A workflow_run receiver would require default-branch deployment, which is not authorized under protected main policy. The pilot workflow is read-only and triggered on PR changes; it does not bypass ChatGPT subscription validation.

## Claim protocol (local acceptance)
The pure claim policy permits one active worker for the entire repository, monotonic generation, unique completed event keys and owner/generation-checked completion. No automatic expiry/takeover; a crashed worker requires independently verified recovery before clearing the claim. The isolated bare Git test demonstrates that two competing same-parent ledger commits cannot both fast-forward. Remote ledger initialization, atomic GitHub connector integration, crash reconciliation and fencing of actual source writes remain unverified. Never treat an in-memory proposal or a successful local test as a live shared lock. Do not activate a second writer.

## Ambiguous ref updates
The reconciliation classifier accepts only exact Git object identities from an independently refreshed ref. An exact candidate observation confirms only that ref value, not ownership, ancestry, fencing or CI. An unchanged parent requires rechecking before any new write; a different head requires investigation; unavailable readback remains unverified. Never blindly retry or force-update. Synthetic remote CAS pilot evidence is recorded in issue #14; the pilot branch is not a live lock and must never be merged.

## Checkpoint artifact validation
Validate bounded UTF-8 JSON, the exact repository/head SHA, expected gate set, run identities, derived decision, and recomputed event key before artifact publication. Duplicate fields and malformed or inconsistent records are rejected. A valid checksum is not authentication; independently retrieve current GitHub run metadata and compare before consuming an event. No artifact alone permits a source write.

## Fresh observation admission
Before treating a stored checkpoint as a candidate, independently retrieve the current branch SHA and fresh exact-SHA workflow metadata. Reject mismatched head or checkpoint, new attempts, conflicting duplicate attempt metadata and missing/unverified bridge gates when applicable. Explicitly derive bridge applicability from PR changed paths; never infer it from artifact content. This read-only policy does not grant ownership or authorize mutations; the caller must verify fresh observations and separately obtain a proven claim. Diagnose failures independently even when a bridge artifact is absent.

## Interrupted worker review
Reconcile an independently retrieved active ledger with a pre-recorded source mutation intent (event, owner, generation, exact parent and candidate). Require independently confirmed worker termination; timeout or silence is not termination. A candidate or parent observation only permits review, not automatic retry, completion or lease release. Missing or unexpected head or mismatched intent holds the claim. Production safety still requires a durable intent store and an enforceable source-write fence; the connector's single-ref CAS cannot establish atomic multi-ref fencing on its own.

## Atomic source-fence experiment
The isolated bare-Git acceptance test demonstrates that an atomic multi-ref push with exact leases for both source and ledger rejects a stale owner even when the source itself has not changed; neither ref moves. A current owner can commit both refs together. This is a synthetic transport experiment, not authorization to force-update remote production refs. Every proposed commit in the experiment is a direct child of the expected ref. The available GitHub connector only exposes single-ref updates, so production multi-ref atomic fencing is not yet established. Keep a single scheduled writer and do not infer provider support from local Git behavior.

## Read-only MCP adapter
The stdio pilot uses the official Python MCP SDK pinned to 1.29.0. In an authorized cloud environment, install requirements-mcp.txt and start mcp_server.py using an MCP host. The two tools inspect supplied checkpoint JSON and ref observations; each reports authorizes_write=false. Neither fetches remote data, accepts a token or file path, executes commands, activates a ChatGPT conversation or mutates a repository. Test acceptance exercises a real SDK client subprocess with initialization, tool listing and calls. Not a hosted HTTP endpoint or installed ChatGPT connector; no user-PC agent is required for the cloud test.

## HTTP transport and ChatGPT connection path
The adapter can optionally bind only to 127.0.0.1 using --loopback-http; the real SDK client verifies Streamable HTTP initialize, discovery and calls. The test bypasses ambient proxies for loopback only. This does not expose a public endpoint. OpenAI documents HTTPS or Secure MCP Tunnel for custom remote servers, and MCP Events explicitly supports authenticated event methods plus verified webhook delivery. ChatGPT Sites also documents Site-hosted MCP tools, with managed authentication and private plugin creation; investigate that path without exposing POS or business records. Event support and outbound callback persistence for a Site must be independently verified before any claim of activation.

## Offline event callback verification
The event verification helper creates a single-use 60-second challenge and prepares exact-byte Standard Webhooks HMAC headers. It rejects non-2xx, expired, duplicate-field, oversized, malformed and mismatched responses. The helper is intentionally offline and process-local: it does not implement subscriptions, durable replay protection, credential storage, callback URL validation or DNS-pinned HTTPS delivery. Those are mandatory before live activation. Contract reference: https://developers.openai.com/plugins/build/mcp-events .

## Offline callback destination admission
Validate only HTTPS DNS names on port 443 and a bounded, independently resolved address set. Reject mixed public/non-public results, IP literals, userinfo, fragments, multicast, private and unsupported IPv6 transition destinations. This is deliberately a strict subset for the pilot; it does not resolve DNS or establish a connection. A future transport must validate each resolution, connect to a validated address directly, preserve hostname verification/SNI, reject redirects, and bound response/time. No live callback delivery is authorized here.

## Synthetic pinned HTTPS transport
The isolated client accepts fresh caller-provided DNS results, validates them, connects directly to a numeric address, and verifies TLS against the original DNS hostname. It transmits the exact signed bytes, rejects redirects and limits response body size. Real TLS tests use an ephemeral self-signed certificate and socket pair with an intercepted dial; no external callback or network address is contacted. Per-operation socket timeouts are not an absolute delivery deadline. Before live use, add a trusted bounded DNS resolver, an absolute response deadline, durable subscriptions/replay protection and host integration. No live event receiver or writer is enabled.

## Absolute callback deadline (synthetic)
The callback client now bounds numeric connect time and installs a monotonic deadline watchdog on a duplicate of the underlying connection, including TLS handshaking and response reads. A real synthetic TLS drip-feed test confirms that repeated short reads cannot extend the total deadline. The pilot does not yet resolve DNS, authenticate a subscription or deliver externally; DNS resolution must be bounded separately.

## Bounded DNS observation (synthetic)
A separate fixed-code Python subprocess obtains numeric system resolver results for a validated fully qualified hostname, with no shell, a bounded result count and timeout. It rejects all unsafe or mixed addresses via destination admission. Tests exercise mocked DNS results and real child-process termination; no public DNS query is required. The system resolver is a host trust dependency, not a DNSSEC guarantee. A future caller must bind this fresh observation to the immediately following pinned TLS connection and enforce a combined deadline; no live callback or event activation is enabled.

## Combined delivery budget (synthetic)
The isolated orchestration helper derives the DNS and pinned HTTPS budgets from one monotonic deadline and rejects expired or late success. No caller-supplied addresses or cached observations are admitted by this helper. The transport also refuses truncated Content-Length responses; tests accept explicit length rejection or TLS read failure, neither can count as delivery. Tests cover deadline accounting and fail-closed paths, while the existing real synthetic TLS and child-process tests cover the component behavior. Not wired to any live subscription or external callback.

## Durable subscription metadata (synthetic SQLite)
The isolated store records principal-scoped identities, callback/event metadata and opaque secret references (not signing secrets), with idempotent creation, transactional generation checks, durable restart and terminal revocation. It records a trusted caller's verification observation; it does not authenticate that caller, perform the challenge or authorize delivery. Temporary test databases only. Production deployment requires an authenticated lifecycle, secure secret storage, delivery/revocation fencing and replay-safe events. No live subscription is created.
